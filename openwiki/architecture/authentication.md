# Authentication Protocols

Authentication models and API handlers live in `packages/core/src/auth.ts`, `packages/core/src/auth/`, `packages/core/src/api.ts`, `passkey.ts`, and `session.ts`. Worker composition enables email and TOTP auth in `packages/worker/src/server-factory.ts`; Node integrations add OAuth/WebAuthn paths under `packages/server/src/auth/`. The client submits protocol messages through `Client`, while the server validates credentials and creates authenticated sessions.

Email signup/login uses verification and recovery codes; TOTP adds second-factor verification; WebAuthn/passkey uses relying-party configuration and challenge verification; public-key authentication protects device/session exchanges; OAuth is a Node/server integration rather than a vault-key transport. Provisioning and device trust must not bypass account authorization or expose vault keys. A session proves authenticated API access, not possession of decrypted vault material.

The client path starts at `Auth._submit` and `LoginOrSignup._authenticate`, creates or continues an `AuthRequest` with an `AuthPurpose`, and calls generated API methods through `Client.call`. Email/SRP flow sends the start-auth request, receives pending authenticator data, submits the proof, and turns the resulting session/auth state into the next account or unlock route. `Client.call` serializes parameters, signs requests with `Session.authenticate` when a session exists, sends through the configured `Sender`, maps transport/server errors to core error codes, and verifies authenticated response HMACs. The Worker receiver applies body-size, timestamp, rate-limit, and idempotency checks before `Server.handle` authenticates context, queues account/org mutations, dispatches the controller, signs the response, and converts failures to `Response.error`. Retry can switch authenticators or continue pending auth; duplicate identical transport bodies replay their stored result, while stale timestamps and malformed bodies fail before domain code.

Core lifecycle vocabulary includes `AuthenticatorStatus` (uninitialized -> pending verification -> active, or disabled), `AuthRequestStatus` (pending -> completed on valid proof, or failed/expired), and `AccountStatus` (available, locked, or disabled). Registration creates a pending authenticator and account data; successful verification activates the authenticator and can establish a session; failed/expired requests do not activate it. Later account lock/disable blocks session use without deleting encrypted vault state, and unlock is a separate vault-key transition. `Authenticator.init` and `AuthRequest.init` create stable IDs, creation timestamps, random salts/tokens, and persistence-ready records; server verification transitions status only after protocol proof succeeds. Email and TOTP implement `AuthServer`; WebAuthn/passkey and OAuth remain separate protocol adapters. MFA is an ordered additional proof after the primary authenticator; trusted-device state permits the intended subsequent session path but does not unlock vault data; recovery is an explicit recovery authenticator/path; admin access is a server authorization role, not a client-side route shortcut. Every path must end in a valid session without implying an unlocked vault; vault keys are established by the subsequent vault/account unlock path.

The focused Worker flow is `packages/worker/test/run-auth-flow-e2e.mjs` with implementation support in `test/auth-flow-e2e.worker.ts`; it covers signup/login and rejection paths such as duplicate email, wrong password, nonexistent account, and revoked sessions. Extension RP coverage is under `packages/extension/test/passkey-rp`; Worker session and crypto contracts cover invalid sessions and provider compatibility. These prove selected primary-auth, session, and crypto invariants, not every status transition: broader MFA, recovery, admin, trusted-device, and native vault-backed passkey guarantees require dedicated tests/proof lanes and should be treated as gaps unless those checks pass. Production native passkey status remains release-blocked; see [native and extension](../operations/native-and-extension.md).

Key invariant: Firefly SSO verification does not create a local account, log a user in, or carry vault-key material; see [Firefly integration](firefly-integration.md).
